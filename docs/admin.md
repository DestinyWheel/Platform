# 管理后台

> 一个路由（`#/admin`），三个页签（概览 / 插件 / 用户）。
> 前端隐藏入口只是礼貌，**真正的边界在服务端**：每个 `/api/admin/*` 都过 `requireAdmin`。

## 1. 为什么放在同一个 SPA 里

后台要做的事和玩家做的事共享同一套东西：同一个 `Session`、同一套 `api`、
同一个 Fastify 实例里的 `host` / `store` / `db`。

拆成独立应用意味着再养一套构建、再配一次 CORS、再发一次版——为了一个几个人用的内部页面不值当。
放在同一个 SPA 里，`isAdmin` 只是大厅顶栏多出来的一个按钮。

## 2. 三个页签

### 概览

一个请求拿全（`GET /api/admin/overview`），所以页面不用并发打五个接口：

| 指标 | 用处 |
|---|---|
| 运行时长 / 内存 RSS | 有没有缓慢泄漏 |
| 数据库类型 | PGlite 还是 Postgres（部署时最常见的困惑） |
| 插件 worker 数 + 具体版本 | 内存里现在活着哪些版本 |
| 有牌桌在用的版本 | 回收不会动它们 |
| 牌桌数（等待/进行/结束） | 是不是有人卡在 lobby |
| 用户 / 管理员数 | 有没有把最后一个管理员降掉 |

每 5 秒自转一次。另有一键备份：整库导出成 gzip JSON 落到 `storage/backups/`，
返回文件路径和每张表的行数，并**自动只保留最近 14 份**（`BACKUP_KEEP` 可调）——
备份不轮转的话，盘是会被慢慢吃满的，而且没人会注意到。
页面上能看到现有备份列表和总占用。**恢复走 CLI**（`scripts/restore.mjs`）——一次恢复会覆盖整库，
这种操作不适合放在一个可能被误点的按钮上。

### 插件

- **上传 .zip**：走完整的发布流水线（见 §4）
- **激活某个版本**：`先加载成功，再切指针`
- **回收闲置 worker**：卸载既不是 active、也没有进行中牌桌在用的版本
- **重新扫描 games/**：开发便利，不用重启服务

表格里每一行显示：游戏、版本、状态（生效中/已退役/待激活/失败）、是否在内存、
构建时间、hash 前 8 位、以及"激活"按钮。失败的版本会把错误直接显示在状态格里——
发布失败最需要的就是那句原因。

### 用户

| 列 | 说明 |
|---|---|
| 权限 | 管理员 / 玩家 |
| 最后登录 | 迁移后能看出谁还没回来过 |
| 局数 | 来自 `match_results` |
| 密码 | 已设置 / 未设置（未设置 = 还没认领的老账号） |

两个操作：

- **设为 / 取消管理员**
- **重置密码** → 生成 12 位临时口令，**只在那一次响应里出现**

重置密码会顺带把 `token_version + 1`，所以对方所有设备立刻掉线；生成的口令服务端不存明文、
不写日志，页面上用一个黄色横条显示一次，关掉就再也看不到。这就是没有邮件系统时"找回密码"的全部实现。

## 3. 接口

| 方法 | 路径 | 说明 |
|---|---|---|
| `GET` | `/api/admin/overview` | 概览（监控 + 计数 + worker 列表） |
| `GET` | `/api/admin/users` | 用户列表（最多 500 条） |
| `POST` | `/api/admin/users/:id/admin` | `{isAdmin}` |
| `POST` | `/api/admin/users/:id/password` | `{password?}` → `{password}`（不传就生成） |
| `GET` | `/api/admin/plugins` | 所有版本 + 内存/在用状态 |
| `POST` | `/api/admin/plugins` | 上传 zip（请求体直接是二进制，不是 multipart） |
| `POST` | `/api/admin/plugins/:gameId/:version/activate` | 切换生效版本 |
| `POST` | `/api/admin/plugins/gc` | 回收闲置 worker |
| `POST` | `/api/admin/plugins/republish` | 重新扫描 `games/` |
| `POST` | `/api/admin/backup` | 整库逻辑备份 |
| `GET` | `/api/metrics` | Prometheus 文本（给采集器用，不是给页面用） |

`/api/metrics` 和 `/api/admin/overview` 是两件事：前者给监控系统抓，格式是文本、稳定优先；
后者给人和页面看，结构可以随需求长。

## 4. 为什么这些按钮是安全的

**上传不会碰线上版本。** 流水线是串行的，任何一步失败就停在原地：

```
解压到 .tmp → 校验 manifest → esbuild 打包 server/client → 源码确定性扫描
→ 同一种子跑两遍，哈希必须一致 → 原子改名进 storage/plugins/<id>/<version>/
→ 写库（status=pending）→ 加载 → 切换 active
```

**激活是先加载后切指针。** `host.setActive()` 会先 `load()`，加载失败直接抛错，
旧版本继续服务——不会出现"指针指向一个跑不起来的版本"。

**回收有白名单。** 只卸载「不是 active 且没有进行中牌桌在用」的版本；之后要回放，
`ensure()` 会按需把那个版本重新加载回来。这条能被验证，是因为插件跑在 worker 里——
卸载 = `terminate()`，模块图真的从内存消失。

## 5. 故意没做的

| 没做 | 理由 |
|---|---|
| 网页上恢复备份 | 覆盖整库，误点代价太大。用 `scripts/restore.mjs`，你需要先敲命令 |
| 删除用户 | 会连带 `match_results` / `ratings` 悬空；有需要直接进库，别做成一个按钮 |
| 改别人的战绩 / Elo | 改数据不如改代码 |
| 牌桌管理（踢人 / 强制结束） | 现在只能靠玩家自己退出。做成按钮之前得先想清楚"超时托管"和"这局算不算战绩"，想不清楚不如不做 |
| 审计表 | 目前管理操作只进结构化日志（`request.log.info`）。真要多管理员再补 |
| 强制下次登录改密 | 现在靠"临时口令只说一次"+ 用户自己改 |

## 6. 一次典型的发版

1. 本地改 `games/<id>/src/server.ts` → `pnpm pack:game <id>` 出 zip
2. 大厅 → 管理 → 插件 → 上传
3. 表格里确认新版本 `active`、旧版本 `retired`，服务没有重启
4. 进行中的老桌仍然锁着老版本，打完自然结束；新开的桌拿新版本
5. 想省内存就点一次「回收闲置 worker」

## 6.1 禁用 / 恢复

插件页每一行有个「禁用」：点了之后这个版本从 active 摘掉，**大厅不再列出，
`#/game/<id>` 详情页显示"不存在或已被禁用"，开房接口直接 400**。

- 已经开着的牌桌不受影响：那些桌锁的是版本号，插件还在内存里，照样能打完
- worker 不会立刻卸载——「回收闲置 worker」会在没有桌用它的时候收掉
- 禁用的版本 **扛得住重启**：自动发布逻辑会跳过 disabled 的版本，不会把它重新激活
- 恢复就是同一行的「启用」，会重新加载并切回 active

## 7. 权限边界

- `requireAdmin` 在**每个** `/api/admin/*` 路由里各自调用，没有全局兜底——故意的，
  新加一个管理路由忘了加检查时，错误是"这个路由能被人访问"，而不是"整个 `/api/admin` 被一个错误的 glob 放行"
- 不能取消自己的管理员权限（`cannot_demote_self`），也不能把最后一个管理员降级
- 前端的路由守卫（`#/admin` + 非管理员 → 回大厅）只是防止画出一个空壳页面，
  校验失败时看到的仍然是接口返回的 403
