# M1 实现说明：真持久化 + 乐观并发 + 动作日志

M0 的局面只活在内存里，重启即丢。M1 把"状态"真正搬进数据库，并把并发模型从进程内互斥换成 **CAS**——这一步做完，才谈得上多实例，也才谈得上插件热加载所需的"版本固定点"。

## 这层解决的三件事

### 1. 状态落库，重启不丢

`tables.state` 是一整份 JSONB。服务启动时不加载任何东西，每次动作都是"读一份 → 算一份 → 写一份"，进程里没有长驻游戏对象。

副作用是免费得到的：**崩溃恢复、滚动发布、多实例**都变成"默认成立"，因为它们都只是"换个进程读同一份数据"。

### 2. 并发从"加锁"换成 CAS

```sql
UPDATE tables SET ..., seq = $new
 WHERE id = $id AND seq = $expected
RETURNING seq
```

影响 0 行 = 读和写之间被别人抢先改了 → 丢弃这次计算结果，重读重算（最多 5 次）。

为什么能这么写？因为 `reduce` 是纯函数，重算没有任何副作用，代价就是一次内存计算。这就是"纯函数 reducer"在工程上的直接回报——**不用锁，不用排队，不用协调者**。

`service.withTable()` 是唯一的写入口，所有操作（加入、开局、落子、超时）都走它。

### 3. 动作日志可重放

`match_actions` 只追加，每行带 `state_hash`。冒烟测试会**真的重放一遍**：

```
start 记录的 action 里存了 { seed, players, options }
  ↓ createInitialState
  ↓ 逐条 applyAction
最终状态哈希 === 库里的 state 哈希
```

这条断言是整套架构的"防伪标签"：只要它成立，回放、观战、审计、AI 自对弈就都是免费的。

## 数据模型

```sql
users(id, name UNIQUE, created_at)
tables(id, game_id, game_version, host_id, status, players jsonb, max_players,
       options jsonb, state jsonb, seq, log jsonb, deadline_at,
       created_at, started_at, finished_at)
match_actions(table_id, seq, actor, kind, action jsonb, effects jsonb, state_hash, created_at)
```

几个刻意的选择：

| 选择 | 原因 |
|---|---|
| 时间戳全用 `bigint` 毫秒 | 避免时区转换和 Date 对象序列化的坑，和前端/引擎的 `ctx.now` 直接对齐 |
| `players` / `log` 存 jsonb | 一次读一次写就是完整局面，不需要 join 多表拼装 |
| `match_actions.seq` 复用 `tables.seq` | 客户端版本号 = 日志位置；加入牌桌会推进 seq 但不写日志，所以日志 seq 允许有空洞 |
| 没有 `match_snapshots` | 骰子这种短局不需要；长局（M3）再加快照表 |

## 数据库怎么选

| 场景 | 配置 | 实现 |
|---|---|---|
| 本地开发 / 测试 | 什么都不用配 | PGlite（嵌入式 Postgres，WASM），数据落在 `.data/pg` |
| 生产 | `DATABASE_URL=postgres://...` | `pg` 连接池 |

两者跑的是**同一套 SQL 和同一套迁移**（`apps/server/src/db/schema.sql`），所以本地验证过的行为到生产不会变。

迁移是个极简 runner：`schema_migrations` 记版本号，没应用过的按顺序执行。M2 起插件不参与 DDL，所以这套 schema 只会向前加列，不会因为插件升级而变。

## 现在的边界

| 项 | 现状 | 后续 |
|---|---|---|
| 超时扫描 | 每秒 `SELECT ... WHERE deadline_at <= now()`，单实例没问题 | 多实例时换 Redis zset，或靠 CAS 去重（现在也靠 CAS，只是扫得勤） |
| 权限 | 昵称即身份 | 需要真账号时加密码/OAuth，JWT 层不用动 |
| 日志量 | 无归档 | 按 `finished_at` 分区；先看数据量再动手 |
| 异常值 | 状态哈希只存不校验 | M2 加载时校验，发现插件不纯就降级该版本 |

## 验证

`pnpm smoke` 现在跑三段：

```
▶ 阶段一：起服务、开桌、打两步        ✓ 打到一半：seq=4
                                      ✓ 服务已完全关闭（Db 实例也销毁了）
▶ 阶段二：同一个数据目录重新起服务      ✓ 重启后恢复：seq=4，比分一致
                                      ✓ 终局：排名 …
                                      ✓ 动作日志：7 条，seq 严格递增
                                      ✓ 重放校验通过
▶ 阶段三：超时兜底                    ✓ 5 秒后代打一步，kind=timeout
```

阶段二用的是**全新的 Db 实例指向同一个数据目录**，所以它证明的不是"进程内缓存还在"，而是"数据真的落盘了"。
