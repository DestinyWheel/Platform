# M2 实现说明：插件热加载

到这一步，"新增/升级游戏不需要重启服务"才算真的成立。M0 时游戏是写死的静态 import，M1 只是把状态搬进了数据库；M2 把游戏本身变成了运行时可发布、可切换版本的东西。

## 发布流水线

后台上传一个 zip（或者启动时扫描 `games/`），依次过六关，任何一关失败都不影响正在跑的版本：

```
zip / 目录
   │
   ├─ 1. 校验     manifest schema、id/version 格式、apiVersion 与宿主大版本匹配
   │               zip 内路径穿越检查
   ├─ 2. 编译     esbuild 打两个自包含 ESM：server.js（Node）/ client.js（浏览器）
   ├─ 3. 静态检查 扫作者源码：Math.random / Date.now / process.* / require / node:fs…
   ├─ 4. 冒烟     把**编译产物**import 进来，同一种子跑两遍，必须得到同样的状态哈希序列
   ├─ 5. 落盘     storage/plugins/<id>/<version>/，先写临时目录再整体 rename 过去
   └─ 6. 激活     写库 → 加载进内存 → 切 active 指针（先加载成功再切）
```

第 4 步是关键设计：**冒烟测的是产物，不是源码**。编译过的代码才是线上真正跑的东西，而"同种子跑两遍哈希一致"这一条同时验证了确定性、可序列化和状态机没卡死。

## 版本固定

这是 M2 唯一的硬约束，也是最容易漏掉的一条：

```
建桌那一刻 → tables.game_version 写入当时 active 的版本 → 之后永不改变
```

后果：

| 场景 | 行为 |
|---|---|
| 发布 0.2.0 | 老桌继续用 0.1.0，新桌用 0.2.0，同一进程内并存 |
| 服务重启 | 从 `game_versions` 恢复 active；老桌按自己锁的版本从磁盘加载 |
| 想让老桌换新规则 | 不行。这是特性，不是缺陷 |

冒烟测试里专门验了这条：上传 0.2.0 之后，老桌的快照 `gameVersion` 仍是 0.1.0，并且还能继续出牌。

## 前端怎么加载

**不用 import map，也不用共享 React。**

插件的前端产物是自包含的 ESM（React、zod 之类统统打进 bundle），浏览器直接：

```js
import('/plugins/dice/0.1.0/client.js')
```

宿主只认三个方法：

```ts
interface GameClient {
  mount(ctx: { root, me, players, send }): void;
  update(snapshot): void;
  unmount?(): void;
  formatLog?(entry): string | null;   // 可选：日志文案也归插件管
}
```

这么做换来三件事：

1. **宿主不被插件锁死框架版本**。插件想用 Preact、Canvas、原生 DOM 都行，M0 那个 React 版的骰子已经改写成原生 DOM 了。
2. **URL 带版本号**，可以 `immutable` 长缓存，发新版天然不冲突。
3. **日志文案由插件渲染**（`formatLog`），宿主里不再有任何 `dice.roll` 这种游戏专属的字符串 —— M0 遗留的知识泄漏清掉了。

## 数据模型

```sql
game_versions(game_id, version, api_version, manifest jsonb, dir, hash,
              status, error, created_at, activated_at)
```

- `status`：`pending | active | retired | failed`
- 一个游戏同时只能有一个 `active`，靠**条件唯一索引**保证：

```sql
CREATE UNIQUE INDEX ux_game_versions_active
  ON game_versions (game_id) WHERE status = 'active';
```

- `hash` 是 server+client 产物内容的 sha256 前 16 位。同版本号但内容不同会被拒绝（`version_conflict`），除非是开发模式下的 `allowReplace`。

## 三种发布方式

| 方式 | 用途 | 入口 |
|---|---|---|
| 启动自动发布 | 开发：`pnpm dev` 起来就有游戏 | `buildApp()` 扫 `games/`，`AUTO_PUBLISH_GAMES=0` 可关 |
| 后台上传 zip | 生产：发新版本 | `POST /api/admin/plugins`（`content-type: application/zip`） |
| 重新扫描 | 开发：改了插件不想重启服务 | `POST /api/admin/plugins/republish` |

打包用 `pnpm pack:game games/dice`，产出 zip 并打印上传命令。

## 权限

`users.is_admin`，第一个注册的人自动成为管理员。上传/激活/重扫都要管理员，冒烟里验了普通用户上传返回 403。

（私人平台够用；要更细的角色再上权限表。）

## 与架构规划的差异

规划里 M2 还包括 **worker 线程隔离**（每个版本一个 worker，退役后 `terminate()` 真正卸载代码）。这次**没有做**，用的是进程内动态 import。

原因：`worker_threads` 的 RPC 会把 `reduce`/`view`/`legal` 的每次调用都变成跨线程结构化克隆，改造面很大；而它带来的唯一好处是"旧版本能真正从内存卸载"。

现在的情况：

- **语义是对的**：缓存按 `游戏@版本` 存，老桌永远拿到老实例，新版本是新的 key —— 行为上和 worker 方案完全一致。
- **代价是内存**：退役版本的模块图会留在进程里，直到重启。

对一个游戏数量在个位数的私人平台，这个代价可以接受。等插件多到需要回收时，再把 `PluginHost.load()` 换成"起 worker + RPC"，接口（`ensure(gameId, version)` 返回 `GamePlugin`）不用动，这也是当初把它抽成 `PluginHost` 的原因。

## 验证

`pnpm smoke` 现在四段：

```
▶ 阶段一  自动发布 dice@0.1.0，开桌打两步
▶ 阶段二  上传 0.2.0 → 老桌仍 0.1.0 且能继续 / 新桌 0.2.0 / 产物可加载 / 非管理员 403
▶ 阶段三  重启（新 Db 实例）→ 老桌按 0.1.0 恢复，active 仍 0.2.0，日志重放哈希一致
▶ 阶段四  超时兜底
```

阶段二全程没有重启服务，是"热插拔"这条需求的直接证据。
