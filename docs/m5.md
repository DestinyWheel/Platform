# M5 实现说明：加固

> 编号注记：计划里 M4 是人机、M5 是加固。这一轮先做了加固，所以它对应 **M5**（动手时曾在对话里叫成 M4，已订正）。

前三个里程碑都是"能玩"。M5 解决的是"敢让别人用"——限流、日志、备份、监控。

## 一、限流

令牌桶，单实例内存实现。选它而不是固定窗口，是因为固定窗口在边界上会放过双倍流量。

| 场景 | 键 | 容量 | 补充速率 |
|---|---|---|---|
| 全局 HTTP 兜底 | IP | 300 | 5/秒 |
| 登录 | IP | 10 | 10/分钟 |
| 建桌 | 用户 | 20 | 20/分钟 |
| 插件上传 | 用户 | 5 | 5/分钟 |
| 聊天（WS） | 用户 | 3 | 1/秒 |
| 游戏动作（WS） | 用户 | 20 | 10/秒 |

超限统一返回 `429` + `retry-after` 头；WS 则回一条 `{ t:'error', code:'rate_limited' }` 消息。

两处细节：

- **`/plugins/*` 和 `/api/health` 不受 IP 限流**——静态产物一个页面要拉好几个，健康检查是探活用
- **桶会定时清扫**（5 分钟一次），否则被大量临时 IP 刷过之后内存会缓慢上涨

键用 IP + 用户两种粒度：登录防的是撞库（按 IP），业务操作防的是单个账号刷（按用户）。

## 二、日志

Fastify 本来就是结构化 JSON 日志。这次补的是**能把一次调用串起来**：

- `genReqId` 用 UUID，每个请求一个 id，日志里自动带
- 关键业务动作显式记录结构化字段：

```
{"level":30,"reqId":"…","userId":"…","tableId":"…","gameId":"dice","msg":"建桌"}
{"level":30,"reqId":"…","userId":"…","connectionId":"…","msg":"ws 连接建立"}
```

- WS 连接建立/关闭都记一条，含 `connectionId`，排查掉线时能对上

没引 `pino-pretty`：开发时看 JSON 虽然丑，但线上直接进采集系统更省事。

## 三、备份

`POST /api/admin/backup` 把整库导成 gzip JSON，落到 `storage/backups/<时间戳>.json.gz`。

包含六张表：`users`、`game_versions`、`tables`、`match_actions`、`table_chat`、`match_results`、`ratings`。

为什么是逻辑导出而不是 `pg_dump`：

- 本地跑的是 PGlite，没有 `pg_dump`
- 逻辑导出**引擎无关**，PGlite 和 Postgres 之间可以互搬
- 内容是纯 JSON，出问题能直接肉眼查

恢复用脚本：

```bash
pnpm tsx scripts/restore.mjs storage/backups/xxx.json.gz [--data-dir <目录>]
```

⚠️ **恢复是破坏性的**：先 `DELETE` 再插入。

冒烟里做了完整往返校验：备份 → 导到一个全新的数据目录 → 逐行比对行数，并断言某张牌桌的 `seq` 和**局面哈希**完全一致。

## 四、指标

`GET /api/metrics`（管理员）输出 Prometheus 文本格式：

```
platform_http_requests 1234
platform_http_errors 0
platform_ws_connections 2
platform_ws_actions 87
platform_workers_loaded 2
platform_tables_playing 1
platform_memory_rss_bytes 123456789
platform_uptime_seconds 3600
```

`/api/health` 顺带升级成给人看的版本：db 类型、uptime、内存、worker 数、各状态牌桌数。

## 验证

`pnpm smoke` 阶段八：

```
✓ 限流生效：连续建桌被 429 拦下
✓ 指标可用（15 项）
✓ 备份完成：5.4 KB，users=3 game_versions=3 tables=23 match_actions=60 table_chat=1 match_results=4 ratings=4
✓ 恢复校验：行数一致，牌桌局面哈希一致
```

## 已知边界

| 项 | 现状 | 说明 |
|---|---|---|
| 限流是单实例内存 | 多实例时各算各的 | 要全局配额就换 Redis 实现，接口不变 |
| 备份是一次性快照 | 没有定时任务 | 要定时就挂在 cron / 计划任务上打这个接口 |
| 没有告警 | 只有指标 | 指标能被 Prometheus 抓到，告警规则在那边配 |
| 日志没有采样和轮转 | 全量写 stdout | 交给容器/系统日志处理，应用不管 |
| 没有审计日志 | 只有动作日志 | 管理操作（上传/激活/回收）目前只在应用日志里 |
