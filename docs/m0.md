# M0 实现说明

M0 的目标是**把骨架立住**：一场对局能从开桌走到结束，路径上每个环节都真实存在（而不是假数据）。真游戏、真持久化、真插件热加载留给后续里程碑。

## 已经做到的

| 能力 | 位置 | 说明 |
|---|---|---|
| 登录（昵称即身份） | `apps/server/src/auth.ts` | HS256 JWT，无依赖手写；同名登录复用同一 user |
| 大厅 | `apps/web/src/views/Lobby.tsx` | 游戏列表、开桌、加入/观战，2.5s 轮询 |
| 牌桌生命周期 | `apps/server/src/service.ts` | 建桌 → 加入 → 开局 → 动作 → 结算 |
| 单桌串行化 | `service.ts` 的 `Mutex` | 同一张桌的写操作排队，为 M1 换 DB CAS 留好位置 |
| WS 实时推送 | `apps/server/src/ws.ts` | 订阅/退订/动作/心跳；状态变更后按**每个人自己的视角**推快照 |
| 超时兜底 | `service.ts#tick` | 每秒扫描 `deadlineAt`，到点在**同一把锁**里二次确认后替玩家行动 |
| 状态机 + 纯 reducer | `packages/engine` | `enterPhase` 沿 `next` 链自动推进，`guard` 防死循环 |
| 确定性随机 | `packages/engine` | `mulberry32(state.rngSeed)`，每次动作后推进种子 |
| 插件契约 | `packages/sdk/src/index.ts` | `GamePlugin` / `ActionDef` / `StateDef` / `Effect` / `PublicView` |
| 示例游戏 | `games/dice` | 2–4 人、3 轮、超时自动掷骰、并列排名 |
| 前端游戏组件 | `apps/web/src/games/dice/DiceGame.tsx` | 通过 `GameProps` 统一入参，M2 换成动态 import 时签名不变 |

## 故意的简化（M1/M2 要还的技术债）

| 简化 | 现状 | 后续 |
|---|---|---|
| 存储 | `MemoryStore`（进程重启即清空） | M1 换 Postgres，接口 `Store` 已抽好 |
| 并发 | 进程内 `Mutex` | M1 换 `UPDATE ... WHERE state_version = ?` 的 CAS |
| 广播 | 进程内 `EventEmitter` | 多实例时换 Redis pub/sub，`EventBus` 接口不变 |
| 插件注册 | 静态 import 两处 | M2 扫描目录 + 版本表 + worker 隔离 |
| 推送粒度 | 每次变更推全量快照 | M3 换 JSON Patch，按 `seq` 补差 |
| 日志 i18n | 宿主里硬编码 `apps/web/src/log.ts` | M2 读插件 `locales/*.json` |
| 鉴权 | 昵称即账号 | 需要真账号时加密码/OAuth，JWT 层不用动 |

## 关键不变量（改代码时别破坏）

1. **插件不碰 I/O**：没有 DB、没有 socket、没有 `Date.now()`、没有 `Math.random()`。全部走 `ctx`。
2. **超时和真人落子走同一条路径**：`applyTimeout` 只负责"决定动作"，真正推进仍调 `applyAction`，否则回放会分叉。
3. **视图裁剪在服务端**：客户端只拿到 `plugin.view(...)` 的结果，拿不到完整 state。
4. **`seq` 只增**：客户端丢弃小于当前 `seq` 的快照，天然抗乱序。
